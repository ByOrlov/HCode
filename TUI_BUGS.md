# TUI Render Bug Audit

Анализ рендера HCode TUI (`src/tui/`) в сравнении с JS-версией
(`kimi-code/packages/pi-tui/`). Ничего не исправлено — только зафиксировано.

---

## Критичные

### 1. Нет защиты от overwide lines в `diff_render` / `full_render`

**Где:** `src/tui/app.cr:2052` (`full_render`), `src/tui/app.cr:2065` (`diff_render`)

JS `doRender` перед выводом транкает каждую строку до ширины терминала через
`sliceByColumn` (tui.ts:1296-1303). Это защитный барьер: ни одна строка не
выходит за `terminal.cols`, что бы ни вернули компоненты.

В Crystal обе функции пишут строки как есть. Любой компонент с off-by-one в
расчёте ширины, или wide-grapheme на границе, производит строку шире терминала:
правый бордер уезжает, появляется мусор, съезжает курсор. Это систематический
класс багов, а не один edge-case.

**Сравнение:**
- JS: `if (lineWidth > width) newLines[i] = sliceByColumn(line, 0, width, true)`
- Crystal: строки выводятся напрямую, без проверки.

### 2. `wrap_text` игнорирует display width

**Где:** `src/tui/app.cr:3413`

Сравнивает `line.size` (число codepoints) с `max_width`, а не `visible_width`.
Для CJK/эмодзи одна кодовая точка занимает 2 колонки — строка из 20 японских
символов при `max_width=80` пройдёт проверку (`20 <= 80`), уйдёт в `[line]` и
отрисуется шире терминала. `wrap_line` в markdown (markdown.cr:553) сделан
правильно через `visible_width`, а `wrap_text` для user-сообщений и ошибок —
нет. Несоответствие в одном и том же проекте.

Затронутые вызовы:
- `render_message` для `role == "user"` (app.cr:2201)
- `render_message` для `role == "error"` (через split, не wrap, но тоже без
  учёта width)

### 3. `title_visible` не учитывает ANSI-коды

**Где:** `src/tui/app.cr:2458`

Возвращает `title` как есть, включая escape-коды Rejected-бейджа. Затем
`title_display.size` (app.cr:2440) считает codepoints вместе с `\e[…m`, поэтому
`trailing = horz_len - title_display.size` становится отрицательным. `clamp(0..)`
спасает от крэша, но верхняя граница план-бокоса короче расчётной: `┐`
съезжает влево относительно `└`.

## Заметные

### 4. Отсутствует single-grapheme guard в `wrap_editor_line`

**Где:** `src/tui/app.cr:2791`

JS `wordWrapLine` (editor.ts:172-181) явно проверяет: если grapheme неделим и
шире `maxWidth` — не рекурсировать, оставить как есть. В Crystal force-break
(app.cr:2834-2840) разрезает по кластеру, но если один кластер шире `max_w`
(CJK при `max_w=1`), он попадает в чанк шириной 2 на терминале шириной 1.
Курсор и правый бордер разъедутся. Не краш, но визуальный баг в узких окнах.

### 5. FIFO width cache с O(n) eviction

**Где:** `src/tui/char_width.cr:27-40`

`WIDTH_CACHE_SIZE = 4096`, eviction через `@@width_cache.first_key?` + `delete`.
Crystal `Hash` сохраняет порядок вставки, поэтому FIFO семантически корректен.
Но `delete(first_key)` на 4096+ записях — O(n) пересчёт хэша при каждой вставке
после заполнения.

JS-версия использует LRU. При больших дампах (стриминг тысяч строк) разница
ощутима: Crystal будет тратить лишнее время на eviction при каждом новом cache
miss сверх 4096. AGENTS.md для pi-tui прямо отмечает это как известное узкое
место с трешингом ~30ms/frame.

### 6. `@max_lines_rendered` не сбрасывается при усадке контента

**Где:** `src/tui/app.cr:2060`, `2149`

`full_render` вызывается при `content_shrunk` (app.cr:1922-1924), но внутри не
сбрасывает `@max_lines_rendered` — присваивает `new_lines.size`. Затем
`diff_render` (строка 2149) снова растит максимум. Если в каком-то сценарии
`content_shrunk` перестанет срабатывать (например, размеры совпали), дифф-рендер
оставит фантомные строки снизу — строки, которые больше не существуют в
`new_lines`, но физически присутствуют на экране, потому что их никто не стёр.

JS имеет явную ветку `clearOnShrink` (tui.ts:1385) с `fullRender(true)`.

### 7. Нет `applyLineResets` — нет гарантии `\e[0m` на конце строк

**Где:** `src/tui/app.cr:2052`, `2124`

`full_render` добавляет `\e[0m\e[K` после каждой строки (app.cr:2057).
`diff_render` пишет только `\e[2K` перед строкой (app.cr:2126) — без `\e[0m`
после. Если строка в `new_lines` не заканчивается на `ANSI.reset`, стиль
утечёт в последующие элементы (бордеры, курсор).

JS отдельно проходит `applyLineResets` по всем строкам (tui.ts:1305), гарантируя
завершающий reset. В Crystal полагаются на то, что каждый рендерер сам закрывает
`reset`. Хрупко: один забытый `ANSI.reset` в любом из ~20 `render_*` методов
даёт цветовое растекание.

## Мелкие / архитектурные

### 8. `extract_last_color` обрабатывает только CSI, игнорирует OSC/APC

**Где:** `src/tui/markdown.cr:670`

Идёт по `\e[…m`, а `CharWidth.extract_ansi_code` умеет CSI/OSC/APC. В практике
TUI OSC почти не встречается в тексте сообщений, но несоответствие существует —
если OSC-код попадёт в обёрнутую строку, цветовая поддержка при переносе
сломается.

### 9. `break_long_token` использует `codepoint_width`, не `grapheme_width`

**Где:** `src/tui/markdown.cr:655`

Не учитывает VS16-промоцию (`⚠️` = width 2) и ZWJ-эмодзи внутри одного длинного
«токена». `grapheme_width` (char_width.cr:275) обрабатывает эти случаи, но
`break_long_token` его не вызывает. Узкий случай, но путь переноса параграфов
чуть менее точен, чем мог бы быть.

### 10. `render_welcome_box` не clamp на `box_w < 2`

**Где:** `src/tui/app.cr:2627`

`"─" * (box_w - 2)` при `box_w=0..1` даёт отрицательный repeat. В Crystal
`String * -n` возвращает `""` (safe от крэша), но логика сломана — рамка
схлопывается. При `box_w < 14` (ширина лого) ASCII-лого выходит за правую
границу без транкации.

### 11. Нет обработки изменения высоты терминала

**Где:** `src/tui/app.cr:1921`

Crystal проверяет только `size_changed` (cols или rows). JS отдельно различает
`widthChanged` и `heightChanged` с разной логикой — height-изменение в Termux
(софт-клавиатура) не вызывает полный перерисов. В Crystal любое изменение
размера ведёт к `full_render`. Не баг, но потенциальное мерцание на мобильных.

## Сводная таблица: Crystal vs JS

| Аспект                          | JS (pi-tui)           | Crystal (hcode)              |
|--------------------------------|-----------------------|------------------------------|
| Truncate overwide lines        | ✅ всегда              | ❌ нет                        |
| `wrap` по display width        | ✅ везде               | ⚠️ только markdown            |
| Single-grapheme guard в editor | ✅ явный               | ❌ нет                        |
| `applyLineResets` (гарантия reset) | ✅ отдельный проход | ❌ надеется на рендереров     |
| Width cache                    | LRU                   | FIFO + O(n) eviction         |
| Height-change handling         | отдельная ветка        | общий `size_changed`         |
| OSC/APC в extract_last_color   | n/a (другой путь)     | ❌ только CSI                 |

**Самые опасные: №1 и №2** — проявляются на обычном контенте (CJK, эмодзи,
длинные токены) в обычных терминалах, не только на edge-cases. Остальное —
про устойчивость при деградации условий (узкие окна, большие дампы,
забытый reset).
